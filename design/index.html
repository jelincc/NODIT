01문제 정의

지금 Overview 화면의 문제

로그인 직후 가장 먼저 보이는 화면인데도, 정작 사용자가 확인하고 싶은 정보는 뒤로 밀려 있습니다.

프로모션 배너가 최우선

광고 배너 2개가 첫 화면의 약 30%를 차지합니다. 실제 사용 데이터는 그 아래, 스크롤해야 나타납니다.

핵심 정보는 스크롤 이후

플랜, 사용량, 요청 수처럼 가장 자주 확인하는 정보를 보려면 평균 3번 스크롤해야 합니다.

텅 빈 첫 화면

신규 가입자는 항상 0으로 채워진 그래프만 보게 되고, 다음에 무엇을 해야 하는지 안내받지 못합니다.

흩어진 업그레이드 버튼

같은 목적(더 많은 리소스 필요)의 버튼이 See Plans, Contact Us, Upgrade 세 군데에 따로 놓여 있습니다.

02제안 방향

Overview를 “진입점”으로 다시 그렸습니다

Nodit을 쓰는 사람은 개발자만이 아닙니다. Treasury, Operations, Compliance, Data팀까지 — 서로 다른 다섯 가지 목적이 하나의 콘솔을 함께 사용합니다. Overview는 이 목적들을 가장 먼저 보여주는 화면이어야 한다고 생각했습니다.

BUILD · 개발 OPERATE · 운영 MANAGE · 자산관리 INVESTIGATE · 조사 ANALYZE · 분석
직군마다 화면을 따로 만드는 방법도 검토했습니다. 하지만 Wallet, Transaction, Asset 같은 데이터는 다섯 가지 목적이 모두 함께 참조하는 데이터였습니다. 그래서 화면을 나누는 대신, 하나의 Overview 안에 다섯 개의 입구를 두는 방법을 선택했습니다.

03사용자와 목적

다섯 가지 목적, 다섯 가지 시작점

직무 이름이 아니라 “무엇을 하려고 왔는가”를 기준으로 정리했습니다.

Job사용자목표핵심 데이터대표 흐름
BUILDWeb3 Developer · CTOAPI·Node로 서비스에 온체인 데이터 연결API, Key, UsageAPI → Project → Key → Webhook
OPERATE거래소·Custody Operations입출금·거래 상태 확인Transaction, TransferTransaction → Transfer → Wallet
MANAGETreasury · Finance보유 자산 현황 파악Balance, PortfolioAssets → Wallet → Chain
INVESTIGATECompliance · Risk지갑·거래 활동 추적Wallet Activity, HistoryWallet → Transaction → History
ANALYZEData Analyst · BI대규모 데이터를 사내에서 분석Dataset, SchemaDataset → Datashare → Pipeline

04정보 구조

목적(Job)과 관리(Admin)를 분리했습니다

Build·Operate·Manage·Investigate·Analyze는 업무 목적이고, Project·API Key· Billing·Team은 제품 관리입니다. 두 축을 같은 depth에 섞지 않았습니다.

05연결된 데이터

다섯 개의 화면은, 결국 같은 데이터를 봅니다

Wallet, Transaction, Transfer, Asset — 이 네 가지가 다섯 가지 목적을 모두 연결합니다. Overview를 하나로 유지한 이유입니다.

06가설과 검증

가설로 남겨, 검증할 수 있게 했습니다

H1 · Job 기반 진입점은 발견 가능성을 높입니다

가설사이드바를 기능명 대신 목적(Job)으로 구성하면, 비개발 직군도 원하는 화면을 더 빠르게 찾을 수 있습니다.
검증 방법직군별로 같은 과제를 주고, 원하는 화면을 찾기까지 걸리는 시간과 정확도를 기존 화면과 비교합니다.
성공 기준5개 직군 평균 10초 이내 도달, 정확도 80% 이상.

H2 · 공유 데이터 구조는 Job 간 이동을 더 쉽게 만듭니다

가설Wallet·Transaction 같은 공통 데이터를 중심에 두면, 한 화면에서 발견한 이슈를 다른 화면에서 바로 이어 조사할 수 있습니다.
검증 방법Job 간 이동 버튼의 클릭률과, 클릭 이후 조사 완료율을 추적합니다.
성공 기준클릭 후 세션 내 완료율 60% 이상.
